# Compose identity and database setup

- The PostgreSQL bootstrap identity is `vulnsuite_bootstrap`. Only the database container receives its password. API, workers, scheduler and optional legacy dashboard connect as `vulnsuite_app`, created with `NOSUPERUSER NOBYPASSRLS NOCREATEDB NOCREATEROLE NOINHERIT NOREPLICATION`.
- The application role has database connection and public-schema creation permissions so API startup can create its tables and install forced row security. It owns the tables it creates. A separate migration role and deployment-managed DDL can further restrict production runtime privileges; the supplied development bootstrap does not implement that separation.
- Copy `deploy/auth.env.example` to a private file outside source control. Generate two independent passwords, for example with two separate `openssl rand -hex 32` invocations. The application password must contain 32–128 letters, digits, underscores or hyphens so it is valid directly in the configured database URL. Bootstrap credentials must be distinct and at least 32 characters. Provision secrets through your normal secret manager in production.
- Replace the example OIDC issuer and public JWKS endpoint with the exact trusted provider values. Use a dedicated API audience and configure signed UUID tenant and application-role claims. The Compose bundle uses remote HTTPS JWKS; offline key-file deployments require an explicit read-only JWKS mount and the file-based auth settings described in the protection authentication guide.
- From the directory containing `pyproject.toml`, validate interpolation without printing resolved secrets: `docker compose --env-file /private/vulnsuite.env -f deploy/docker-compose.yml config --quiet`. Once reviewed, start the bundle with the same arguments and `up -d --build` instead of `config --quiet`. Required missing variables cause Compose to stop; the initializer also rejects unsafe application-password syntax and reused credentials.
- A new **empty** PostgreSQL volume runs `deploy/postgres/10-application-role.sh` once. PostgreSQL's [official image initialization rules](https://hub.docker.com/_/postgres) leave existing data directories intact and do not rerun initialization scripts. The script obtains its password through [psql environment variables](https://www.postgresql.org/docs/16/app-psql.html), quotes it as an SQL literal, and stops on SQL failure.
- The Docker build reconstructs `/app/pyproject.toml` plus `/app/vulnsuite/` from this checkout's package-directory layout. Explicit source copies and `.dockerignore` exclude deployment credentials, databases, key files and caches from the build context. Console HTML/JS/CSS are declared package data and included in the installed package. For source-based execution, run from this package directory's parent so `vulnsuite` is importable; the current source layout is not a conventional editable-install project root.
- Put the API behind your HTTPS ingress. Browser login and MFA belong to your identity provider; callers send its access token and the matching `X-Tenant-Id`. The protection service's authenticated `/console` is the supported SOC UI. The old Streamlit dashboard is excluded by default using the `legacy-dashboard` profile and bound to localhost when explicitly enabled; it still permits manual tenant selection and must not be exposed as an authenticated multi-tenant interface.

## Existing PostgreSQL volumes

Changing Compose environment variables does **not** change database roles, passwords, table ownership or the existing volume. The former Compose role `vulnsuite` was created as a superuser and will now be rejected by API startup. Do not delete the volume or demote the only administrative role as a shortcut.

1. Take and verify a database backup, record the actual volume name and existing role/ownership state, and schedule a maintenance window. Stop application writers while retaining a verified administrator connection. Preserve the old volume and credentials for rollback.
2. Using that existing administrator connection, create a separate `vulnsuite_bootstrap` administration role if needed and a new `vulnsuite_app` role with the exact restricted flags shown in the initializer. Set their independent passwords interactively (`\password`) or through your approved secret workflow. Do not expect changed `POSTGRES_PASSWORD` environment values to rotate existing credentials.
3. Grant the application role database `CONNECT` and public-schema `USAGE, CREATE`. Transfer ownership of **only the VulnSuite `public.assets` and `public.findings` tables and their associated sequences, if any**, to `vulnsuite_app`; inventory any additional application objects first. Avoid `REASSIGN OWNED` on an existing superuser, which could transfer unrelated objects. The application must own its tables to install/upgrade the policies during startup.
4. Apply the current `RLS_DDL` from `vulnsuite/core/db.py` in one transaction, including `ENABLE` and `FORCE ROW LEVEL SECURITY`, explicit `WITH CHECK`, and the transaction tenant setting policy. Verify no other permissive policies grant unintended access. The new initializer is intended for fresh databases; review its grants individually for an existing environment instead of blindly rerunning it.
5. Configure Compose with the new credentials and issuer/JWKS values. Start the API first and validate it using the application identity. Confirm `rolsuper=false`, `rolbypassrls=false`, and `rolcreaterole=false` for `vulnsuite_app`. Confirm `relrowsecurity=true` and `relforcerowsecurity=true` for both tables. Verify that two signed tenant identities cannot read or mutate each other's rows, missing tenant context exposes no rows, and writes with a mismatched tenant fail.
6. Start workers and scheduler after API/database validation. Review and revoke the old application's login and unnecessary grants after consumers have migrated; retain an independently secured administrator identity. If validation fails, stop the new application and use the preserved backup/role configuration under the maintenance plan. Do not restore old public unauthenticated access.

Validation here is static: YAML/environment validation, simulated Python package discovery and shell/SQL contract checks do not run Docker, initialize PostgreSQL, or contact an identity provider. The full scanner-image download/build, scanner binary architecture compatibility and image runtime remain unvalidated. A fresh-volume staging startup, existing-volume migration rehearsal, and signed cross-tenant database checks remain deployment requirements.
