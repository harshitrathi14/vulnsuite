# Enterprise identity and role configuration

- The scanning API now verifies signed access tokens from a configured external identity provider. The previous arbitrary bearer-token stub is removed. Missing identity configuration denies access.
- Use your organisation's existing SSO application and its authorization-code flow with PKCE to obtain an **API access token**. Passwords and interactive login are handled by that provider; this module does not implement an identity provider or browser login session.
- Configure an exact HTTPS issuer, a dedicated API audience and exactly one public JWKS source using `auth.example.env`. Provision issuer and JWKS URL together from your provider's trusted metadata. Tokens cannot select a key URL. Remote key downloads require HTTPS, reject redirects and ignore proxy environment variables.
- Configure the identity provider to emit `sub`, `iss`, `aud`, integer `iat` and `exp`, a UUID `tenant_id`, and `roles`. An optional `nbf` is checked. `tenant_claim` and `roles_claim` support dot paths such as `realm_access.roles`; use `tid` only when that identity-provider tenant represents the intended VulnSuite organisation.
- Limit role values to `admin`, `analyst`, `viewer`, or `auditor`. Unknown, missing and empty role assignments deny access. One token may carry several roles. Assign roles centrally in the identity provider; application callers cannot choose roles in headers or request bodies.
- Every scanning API request requires `Authorization: Bearer <access-token>` and `X-Tenant-Id: <UUID>`. The header must match the **signed token tenant** before a database session is opened.
- Run the scanning API and workers with a PostgreSQL `NOSUPERUSER NOBYPASSRLS` role. API initialization refuses a role that bypasses row security, installs explicit read/write tenant policies, and forces row security for table owners. Application sessions bind the verified tenant with transaction-local `set_config` on every transaction. Production schema migrations must install the same policies. The SQL and session lifecycle have isolated tests; an actual PostgreSQL staging check of cross-tenant reads/writes remains required.
- Admins can perform discovery and analyst operations. Analysts can create assets, start scans and use analyst routes. Viewer/auditor access follows the explicit read/report route policies. Protection-service permissions are assigned separately in its operator RBAC layer using the same verified identity.
- Only RS256 with RSA keys of at least 2048 bits and ES256 with P-256 are supported. Public JWKS must contain no private or symmetric material. Configure `jwt_algorithms` explicitly for your identity provider.
- Tokens expire, must have a current issue time and may not exceed the configured maximum lifetime (8 hours by default). Prefer shorter provider token lifetimes for privileged operators. Token revocation is effective at expiry; live introspection/revocation and per-request group lookups are not implemented.
- Keys are cached for 5 minutes by default, with a maximum configured interval of 1 hour. Publish new public keys at least one cache interval before issuing tokens with them; keep old verification keys until old tokens expire. A failed refresh denies authentication and does not keep using expired cached keys. Removing a key becomes effective after the cache interval.
- For an offline JWKS, mount an operator-maintained public JSON file read-only and rotate it atomically. Do not enable `jwks_url` at the same time. Restart processes after changing issuer, audience, claim mappings or algorithm settings.
- Validate with a staging provider: valid viewer access, denied viewer mutations, admin access, wrong-tenant rejection, expiration, a retired signing key and an unavailable key endpoint. Unit tests exercise forged signatures, unsafe headers, invalid claims, role denial and tenant isolation, but do not replace staging identity-provider validation.

The implementation follows the [JWT Best Current Practices validation guidance](https://www.rfc-editor.org/rfc/rfc8725.html), especially explicit algorithm, issuer and audience checks.
